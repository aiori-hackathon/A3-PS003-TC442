The problem (AIORI-3 · PS-003)

Roadside sensors normally stream raw traffic data to the cloud. Federated learning keeps data at each junction and only sends model updates. We measure what that really costs and gains: accuracy, fairness across junctions and bytes. Our motto: measure before you federate.

What happens in each stage

  1. Centralised: all junctions upload raw data; one model trains on everything (accuracy reference).
  2. FedAvg: each round the server sends the model down, junctions train on their own data, the server averages their updates weighted by data size. Every byte is measured.
  3. PulseFed (our idea): junctions whose model barely changed skip the next round; at least 2 always talk and nobody sleeps more than 2 rounds.
  4. PulseFed v2 (follow-up): same skipping, but the server reuses a sleeping junction's last update so every road group still counts.

The data

UCI Traffic Flow Forecasting: 36 sensors, 15-minute volumes, 1261 training and 840 later test steps (chronological, verified). Task: predict each sensor's volume 15 minutes ahead. Our audit found the file has 48 columns (documentation says 47) and that the provided target is 30 minutes ahead, so we rebuilt the true 15-minute target.

The junctions

Four simulated junctions. Non-IID: each junction owns a group of sensors, from the quietest to the busiest roads. IID: rows shuffled evenly (only in “Run one method”).

Honest notes

Live runs use one seed and fewer rounds so they finish quickly, so numbers differ slightly from the 3-seed, 30-round results. Browser arithmetic (WebAssembly) can differ from a laptop in the last decimal places; PulseFed's talk-or-sleep choices are sensitive to such tiny differences, so its live numbers can differ more. The Full results tab (our Python code run on a laptop, 3 seeds) is the official reference. This is a simulation; no formal privacy guarantee is claimed.
